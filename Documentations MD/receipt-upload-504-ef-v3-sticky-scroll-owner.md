# DOC-019 — Receipt upload 504, EF v3 bump, and truly frozen Actions column

**Status:** in progress
**Last updated:** 2026-06-30
**Area:** Expense submission — receipt upload; Edge Function reliability; Review table usability

---

## Summary

Phase 4 of the receipt finalization work. Three scoped issues fixed:

1. **Direct receipt upload 504 + CORS warning** — browser uploads to self-hosted Supabase Storage time out (504 Gateway Timeout) because the reverse proxy has an insufficient timeout or body-size limit. The 504 response lacks CORS headers, producing a secondary CORS error. Root cause is infrastructure; the frontend fix adds graceful failure tracking and a retry button.

2. **EF runtime 500 / no effect after code changes** — local code changes do not take effect until the Edge Function is re-deployed to the Coolify server. VERSION bumped to `"receipt-finalizer-v3"` to distinguish the current deploy from the v2 binary.

3. **Actions column not truly frozen** — Phase 3 added `sticky right-0` classes but the shared `Table` component wraps every `<table>` in `<div className="relative w-full overflow-auto">`, which becomes the sticky-anchor scroll container. The outer `relative overflow-x-auto` div we added in Phase 3 was not the scroll owner so sticky never worked in the browser. Fixed by adding a `noScrollWrapper` opt-in prop to the shared `Table` component and restructuring all 4 review tables to use a single scroll container.

---

## Root cause details

### Issue 1 — Direct upload 504

The browser calls `supabase.storage.from('receipts').upload(uploadPath, file, ...)` which hits:

```
Browser → Coolify reverse proxy (Traefik or NGINX) → Kong gateway → Supabase Storage (MinIO)
```

For large files (> a few MB) or slow connections, the proxy's `proxy_read_timeout` (default 60s) or `client_max_body_size` limit causes:
- `504 Gateway Timeout` response from the proxy
- The 504 response is generated by the proxy itself (not by Supabase Storage), so it has **no CORS headers**
- Browser reports both a timeout error AND a secondary CORS error

**Infrastructure fix required** (cannot be applied from source code — must be done in Coolify):
- For Traefik (most common in Coolify): add `traefik.http.middlewares.my-middleware.buffering.maxRequestBodyBytes=52428800` (50 MB) and increase response timeout
- For NGINX: set `client_max_body_size 50m; proxy_read_timeout 120s; proxy_send_timeout 120s;`
- Verify change by uploading a large file and checking the proxy logs

**Frontend fix** — graceful failure handling (see below).

### Issue 2 — EF version (receipt-finalizer-v2 → v3)

The Edge Function is a Deno binary deployed to Coolify's persistent volume at:
```
/data/coolify/services/{SERVICE_ID}/volumes/functions/finalize-expense-receipts/index.ts
```

Changes to the local file are NOT picked up until the edge-runtime container restarts or the file is manually synced via the deploy script (`scripts/deploy-edge-functions-coolify.ps1`). The VERSION constant bump makes it easy to verify in Coolify EF logs whether the new code is actually running.

### Issue 3 — Sticky column not truly working

**Root cause:** `src/components/ui/table.tsx` wraps every table in:
```tsx
<div className="relative w-full overflow-auto">   ← THIS is the sticky anchor, not any outer div
  <table .../>
</div>
```

Our Phase 3 outer `<div className="relative overflow-x-auto">` was a **sibling** of the inner overflow-auto div, not its parent, so `sticky right-0` on `<th>`/`<td>` always anchored to the inner `overflow-auto` div. Since the table width equalled the inner div width, stickiness was invisible.

**CSS fact:** `position: sticky` anchors to the nearest scrolling ancestor. Two nested overflow containers means the inner one wins.

## Fixes

### A. `src/components/ui/table.tsx` — `noScrollWrapper` opt-in prop

```tsx
// Before (every Table creates an overflow-auto wrapper):
const Table = React.forwardRef<HTMLTableElement, React.HTMLAttributes<HTMLTableElement>>(
  ({ className, ...props }, ref) => (
    <div className="relative w-full overflow-auto">
      <table ref={ref} className={cn("w-full caption-bottom text-sm", className)} {...props} />
    </div>
  ),
);

// After (noScrollWrapper bypasses the inner wrapper):
type TableProps = React.HTMLAttributes<HTMLTableElement> & { noScrollWrapper?: boolean };

const Table = React.forwardRef<HTMLTableElement, TableProps>(
  ({ className, noScrollWrapper, ...props }, ref) => {
    const table = <table ref={ref} className={cn("w-full caption-bottom text-sm", className)} {...props} />;
    return noScrollWrapper ? table : <div className="relative w-full overflow-auto">{table}</div>;
  },
);
```

**Backward compatible:** all existing Tables without `noScrollWrapper` are unchanged.

### B. Review tables — single scroll owner restructure

Applied to all 4 routes: `/admin/expenses` (AdminPanel), `/review` (EngineerReview), `/expenses/batch/:batchId/review` (BatchExpenseReviewPanel), `/cashier/approved` (AccountantApprovedExpenses).

**Before (broken — two scroll containers):**
```tsx
<div className="relative overflow-x-auto -mx-4 sm:mx-0">        {/* outer — NOT the sticky anchor */}
  <div className="inline-block min-w-full align-middle">          {/* middle wrapper */}
    <Table className="min-w-full">                                {/* Table adds overflow-auto div */}
      ...
      <TableHead className="sticky right-0 z-30 ..."/>           {/* anchors to Table's inner div */}
```

**After (correct — one scroll container):**
```tsx
<div data-testid="*-scroll-container"
     className="relative w-full overflow-x-auto -mx-4 sm:mx-0">  {/* SOLE scroll container */}
  <Table noScrollWrapper className="min-w-max">                   {/* no inner overflow-auto */}
    ...
    <TableHead data-testid="*-actions-header"
               className="sticky right-0 z-30 ..."/>              {/* anchors to the one outer div */}
```

**Changes per file:**

| File | Route | data-testid prefix |
|------|-------|--------------------|
| `src/pages/AdminPanel.tsx` | `/admin/expenses` | `admin-expenses` |
| `src/pages/EngineerReview.tsx` | `/review` | `engineer-review` |
| `src/components/BatchExpenseReviewPanel.tsx` | `/expenses/batch/:id/review` | `batch-review` |
| `src/pages/AccountantApprovedExpenses.tsx` | `/cashier/approved` | `accountant-approved` |

Each file gains three `data-testid` attributes:
- `{prefix}-scroll-container` — the outer scroll div
- `{prefix}-actions-header` — the sticky `<TableHead>`
- `{prefix}-actions-cell` — the sticky `<TableCell>` (on each row)

### C. `src/components/FileUpload.tsx` — upload state tracking + retry

**Problem:** when the proxy returns 504, the upload silently fails (error toast only), the file is gone from the UI, and the user has no way to retry without re-picking the file.

**Fix:** added `ReceiptUploadState` type and `FailedUpload` interface; failed uploads are tracked in `failedUploads` state and rendered with a Retry button.

```typescript
type ReceiptUploadState = "queued" | "uploading" | "uploaded" | "failed";

interface FailedUpload {
  id: string;
  file: File;
  filename: string;
  errorMessage: string;
  state: ReceiptUploadState;
}
```

**State invariants preserved:**
- `onUploadComplete` is called ONLY on confirmed successful upload (no change from before)
- `setAttachments` is NOT called in the catch block (attachment state never has failed files)
- No `sessionTempMeta` or blob cache entry is created for failed uploads (since `onUploadComplete` isn't called)

**Retry flow:**
1. `catch` block → `setFailedUploads(prev => [...prev, { id, file, filename, errorMessage, state: "failed" }])`
2. UI renders `data-testid="failed-upload-item"` with `data-testid="retry-upload-button"`
3. Retry button → `retryUpload(failed)` → removes from `failedUploads`, re-calls `uploadFile(file)`
4. If retry succeeds → file added to `attachments` via normal success path
5. If retry fails again → re-added to `failedUploads`

## Infrastructure config change required

**This change cannot be applied from source code.** It requires direct access to the Coolify server or its dashboard.

### For Traefik (most common in Coolify)
In the Supabase service's docker-compose labels or Coolify network settings, increase the response timeout:
```yaml
labels:
  - "traefik.http.routers.supabase.middlewares=supabase-timeout"
  - "traefik.http.middlewares.supabase-timeout.buffering.maxRequestBodyBytes=52428800"
  - "traefik.http.middlewares.supabase-timeout.buffering.maxResponseBodyBytes=52428800"
  - "traefik.http.middlewares.supabase-timeout.buffering.retryExpression=IsNetworkError() && Attempts() < 2"
```
Or set a global timeout in Traefik's static config:
```yaml
# /etc/traefik/traefik.yaml
serversTransport:
  forwardingTimeouts:
    dialTimeout: 30s
    responseHeaderTimeout: 120s
    idleConnTimeout: 90s
```

### For Kong (Supabase's built-in gateway)
If Coolify's Supabase stack uses Kong, increase timeouts in Kong's upstream configuration. This is usually done via `KONG_NGINX_HTTP_CLIENT_BODY_BUFFER_SIZE` and related environment variables in the docker-compose.

### Verify after change
Upload a file ≥ 5 MB via the FileUpload component. The upload should complete without a 504. Check Coolify proxy logs for the request latency.
