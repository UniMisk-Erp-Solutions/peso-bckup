## 1. What the system does
1. **PesoWise → Tally:** the admin presses **Sync to Tally** on Reports → Detailed Expense. The server groups expenses by (month, expense type) and builds one **Journal voucher** per group; a small Windows **connector** posts it into TallyPrime and reads it back to verify.
2. **Corrections:** an expense deleted or edited in PesoWise after it was posted is corrected in Tally automatically (the amount is removed from the old voucher; an edit is then re-posted).
3. **Tally → PesoWise:** payments entered in Tally (Dr employee ledger, Cr Cash/Bank) are read by **Sync from Tally** and added to the employee's PesoWise balance as a balance credit (once per voucher).
4. Extras: Tally History (per-employee detail + Reverse Import), a TDL screen inside Tally, a server-side deleted-bill archive, plain error messages for every failure.

## 3. Accounting rules (the part that must stay exact)
**Expense voucher (Journal)**
- One voucher per (month, expense type). Voucher no.: narration `PWT PESO/MM/NN`; MM is the month, NN is the serial from the mapping. Later postings into the same month and type get `-S1`, `-S2`…
- **Debit** the mapped expense ledger (parent group **Indirect Expenses**) with the total. **Credit** each employee ledger `Name-Code` (parent **Sundry Debtors**) with that employee's total. Debit always equals credit.
- Date: last day of the month (default `month_end`) or first day (`month_start`); setting "Voucher date" on the Ledger mapping page. Educational-mode Tally refuses some dates (e.g. 30 June); first-of-month works.
- Empty/"N/A" category → "Miscellaneous Expenses", serial 99. An **unmapped** expense type is a *blocking* issue (the row is not posted).
- Mapping serials are 1–98 (+99). **Each expense type needs its own serial**, so one org with more than 98 types cannot be mapped yet (aliases exist in the config, but there is no wildcard/pattern rule and the UI does not expose them).
- Missing ledgers are created by the connector (create only, never alter); existing ledgers are left alone.
- Each expense is recorded in `pwt_registry` as posted only after the connector read it back from Tally. A conflict (same voucher number, different amounts) stops with "already exists in Tally with different amounts - manual review needed".
- Default mapping (MicroLink): 1 Travelling→Travelling Expenses, 2 Material Purchase→Consumable Stores - URD, 3 Other(Xerox…)→Site Expenses, 4 Laptop Rent→Rent Expenses - Equipment, 5 Hotel/Guest House→Lodging Expenses, 6 Petrol→Conveyance Expenses, 7 Local Manpower→Labour Charges Expenses-URD, 8 Mobile Recharges→Telephone Expenses, 9 Food→Travelling Expenses, 10 Incentive→Incentive Expenses, 99 N/A→Miscellaneous Expenses.

**Corrections (delete / edit)**
- A trigger on `expenses` marks synced expenses dirty. The planner compares mapping-independent facts (amount, voucher month, employee code, expense type) with the registry. Delete → `pwt_deletion_jobs` (reason `deleted`); edit → correction of the old posting (reason `edited`), then a `repost` job, run automatically from the connector heartbeat (`driveEditJob`). Corrections are per Tally company and wait if no connector is online.

**Payments (Tally → PesoWise)**
- Voucher type must equal the exact name saved on the Sync from Tally screen (default "PesoWise Payment"; the connector auto-creates it with parent Payment). **One type at a time**; switching type is safe (a payment is flagged "deleted in Tally" only if the sync that last saw it read the same type).
- Dr side = employee ledger; **the employee is matched by the code at the end of the ledger name only** (`…-<code>`); the name text is ignored. Unknown code / inactive member / code shared by 2 employees → refused with a reason.
- Cr side must be a Cash/Bank group ledger; the group name comparison is case-insensitive (`Cash-in-hand` = `Cash-in-Hand`).
- Skipped, never applied: vouchers narrated `PWT …`, cancelled or optional vouchers, unbalanced vouchers, non-employee ledgers.
- Balance credit goes through the existing balance engine (`_balance_apply_credit_core_v3`); each sync creates a `balance_import_batches` row (mode `balance_credit`), so Reverse Import uses `balance_reverse_import_v3`.
- Edited or deleted vouchers after import are flagged for manual reconciliation; the balance is never changed automatically.

## 4. Pairing and company isolation
- One exe for every company. An admin enters the **exact Tally company name** on the Tally page; the server stores a one-time code (valid 15 min, single use, hash only) tied to that admin's PesoWise organisation and that Tally company.
- The exe sends the code, receives a **long device key**, stores it locally; the server keeps only its hash. All later calls use the key. The connector is locked to **one PesoWise organisation and one Tally company**, and acts only while that company is the active one in Tally.
- One PC (one Windows user) holds **one** pairing; re-running setup and answering "y" replaces it. Two companies on one PC need two Windows users (not built otherwise).
- All companies share one database; isolation is by `organization_id` plus the device key. There is no per-company database or per-company exe. A "company-named download" would only be a file-name change.
- Revoke a connector from the Tally page.

## 7. How a sync runs (technical)
`pwt-start-sync` creates `pwt_sync_jobs` → `pwt-run-job` prepares in slices (read report pages via `report_detailed_expense_rows_v4` → normalise → **plan**; `SLICE_BUDGET_MS=7000`, `NORM_CHUNK_ROWS=1000`) → `pwt_complete_prep_v1` stores batches (masters, report_rows, vouchers) → connector claims batches (`pwt-connector` claim/ack), posts XML to Tally over HTTP (port 9000), verifies, acks. Edit jobs are driven from the connector heartbeat. Inbound: `pwt-inbound` start/claim/submit/finish, validation in SQL `_pwt_inbound_process_v1`.
- **8-second limit:** PostgREST connects as `authenticator` with `statement_timeout=8s`; a per-function SET does **not** override it (tested). A whole-year sync (27k rows) failed in the `plan` phase with "canceling statement due to statement timeout"; 8.7k and 12.6k rows worked. Advice: sync by month. A real fix would split planning into smaller calls (not built).
- Container/host names must stay under 63 characters (DNS label limit). `ship.sh`-style logic is not part of this product; that was a separate demo.

## 8. Errors shown to users
`src/lib/pwt/pwtErrors.ts` (`describePwtError`, `functionErrorText`) maps network loss, expired login, no permission, no connector paired, bad/expired pairing code, too large sync (statement timeout), missing server setup (schema cache), rate limit, timeout, TallyPrime offline, wrong company open, voucher conflict, server error to one plain sentence. Job errors go through `friendlyTallyError` in `pwtSync.ts`. Connector 1.2.7 names network causes (`explainNetworkError` in `runtime.ts`) and gives a next step per pairing failure (`pairingAdvice` in `setup.ts`).

## 12. Tally facts and gotchas
- Tally HTTP/XML on `127.0.0.1:9000`. Verified TDL facts: collection filter `$Narration Contains "PWT PESO/"` works; walk-level `$PWTDeem = "No"` works; a line `Invisible` rule hides rows in exports but **not** on the real screen.
- Company period: the connector reads BooksFrom/StartingFrom and moves both earlier only for PesoWise-only companies; Educational mode refuses some dates for another reason ("Voucher date is missing" can mean either).
- Tally's real group name here is `Cash-in-hand` (small h); that caused "credit side is not a cash or bank ledger" until the check became case-insensitive.
- A bare `<VOUCHER>N</VOUCHER>` in an export is the voucher counter, not a voucher.
- Restored Tally data needs all files (`TranMgr.1800`, `Manager.1800`, `.TSF`…); an incomplete set shows "Migration Required".
- A paired company that already holds PesoWise-style vouchers (older system) causes the voucher-number conflict, because the registry lives in the database, not in Tally. Use a clean company or clear the old `PWT PESO/` vouchers.
- Shell gotchas on the dev PC: heredocs/`node -e` strip backslashes (use the Write tool for regexes); Python is not installed locally (use node); never `rm -rf` through variables (blocked by a safety check; use literal paths); `ssh` inside `while read` loops needs `-n`.
